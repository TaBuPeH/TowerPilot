# Usage-Limit Guard

**When the gate denies an Agent/Workflow dispatch with a `USAGE-LIMIT GATE` reason, follow the wind-down protocol printed in that deny reason verbatim — it is the canonical instruction set (generated by the gate script). Do not dispatch new work, drain in-flight agents, write the resume brief, register the scheduled resume, end the turn.**

> [!note]
> The guard's scripts live locally in this project: `D:\projects\tower\.claude\hooks\usage-limit\`. The guard installs into **user-level** `~/.claude/settings.json`, so once installed it protects every project on the machine — including this one. This skill is the machine-wide reference.

The guard has three parts plus an installer:

| Part | File | What it actually does |
|---|---|---|
| Sensor | `statusline.js` | Runs as the user-level statusLine command (60s refresh); persists `rate_limits.{five_hour,seven_day}` to `~/.claude/usage-limit/state-<sessionId>.json` (+ `state.json` fallback) and renders a usage meter (`⛔ PAUSE` prefix at ≥95%) |
| Brake | `pretooluse-gate.js` | User-level PreToolUse hook, matcher `Agent\|Workflow`; DENIES new agent/workflow dispatches when a window is ≥95% and un-reset; logs every decision to `~/.claude/usage-limit/gate.log` |
| Alarm | `register-resume.ps1` | One-shot Windows scheduled task `ClaudeUsageResume-<sid8>` running `claude --resume <sid> -p …` at window reset + 5 min from `-ProjectDir`; output → `~/.claude/usage-limit/resume-<sid8>.log`; `-Cleanup` removes it |

## Rules

1. **Setup is per-machine, one command:** `node D:\projects\tower\.claude\hooks\usage-limit\setup-usage-limit-guard.js` — merges statusLine + the PreToolUse gate into **user-level** `~/.claude/settings.json` (`.bak` backed up; idempotent; `--revert` removes). Restart Claude Code / reload the window afterwards so the statusline starts.
2. **Never wire the guard into project settings** (a repo `.claude/settings.json`) — a committed statusLine overrides every teammate's personal statusline (user → project precedence).
3. **The deny reason is the wind-down protocol's single source of truth.** This skill points at it; never copy its steps into other docs. If the protocol must change, change the gate script.
4. **Fail-open is a feature, not a bug.** Missing/stale (>30 min) state, null percentages (API-key auth, pre-first-response), or a passed reset time all ALLOW. A sensor problem degrades to pre-guard behavior — never a bricked session. Do not "fix" an inert guard by making it fail-closed.
5. **The resumed session must self-cleanup**: the resume prompt includes the `-Cleanup` invocation — run it. A fired one-shot task left behind is inert but clutters Task Scheduler.
6. **If the installer skips your custom statusline**, the gate still installs (inert, fail-open). To arm the sensor, make your statusline script also pipe its stdin JSON to the guard's `statusline.js`.
7. **The alarm is Windows-only** (Task Scheduler + PowerShell). On macOS/Linux the sensor + brake still work; schedule the resume manually (calendar reminder or cron running `claude --resume <sid> -p "continue"` from the project dir after the reset shown in the deny reason).

## Anti-Patterns

| Wrong | Right | Why |
|---|---|---|
| Keep dispatching agents after a `USAGE-LIMIT GATE` deny ("just one more") | Follow the wind-down protocol immediately | The 95% threshold exists to leave drain headroom; burning it strands in-flight agents at 100% |
| Hand-edit `~/.claude/settings.json` to add/remove the guard | Run the installer / `--revert` | The installer is idempotent, backs up, and migrates old paths; hand edits drift and break `--revert` detection |
| Make the gate deny on missing state "to be safe" | Keep fail-open (Rule 4) | Every fresh session starts with no state; fail-closed would brick all of them |
| Copy the wind-down steps into CLAUDE.md / other skills | Point at the gate script (Rule 3) | Two copies of the protocol diverge on the first edit |

## Troubleshooting

| Symptom | Cause | Fix |
|---|---|---|
| Statusline shows `usage n/a` | No `rate_limits` yet: first API response hasn't happened, or API-key auth | Wait one turn; on API-key auth the guard stays inert by design |
| No statusline meter at all after install | Harness not restarted, or installer skipped an operator-authored statusline | Reload the window; check installer output for the SKIPPED notice (Rule 6) |
| Gate never fires (no `gate.log` lines on agent spawns) | Hook not installed in user settings (gate logs allow-lines regardless of state — zero lines means the hook isn't running) | Re-run the installer; verify `hooks.PreToolUse` in `~/.claude/settings.json` references `usage-limit/pretooluse-gate.js` |
| Scheduled resume didn't restart work | Task fired but headless run failed | Read `~/.claude/usage-limit/resume-<sid8>.log`; resume manually with `claude --resume <sid>` from the project dir |
| Deny cites a reset hours away while the 5h window already reset | The 7-day window is also ≥95% — the gate deliberately cites the LATER reset | Nothing to fix; resuming earlier would hit the weekly wall immediately |

## Verification

1. `echo '{"session_id":"t","rate_limits":{"five_hour":{"used_percentage":50,"resets_at":1900000000}}}' | node D:\projects\tower\.claude\hooks\usage-limit\statusline.js` → prints `5h 50.0% …` and writes `~/.claude/usage-limit/state-t.json`.
2. Spawn any agent, then check `~/.claude/usage-limit/gate.log` — a `decision=allow` line with your session id proves the brake is live.
3. Installer: run twice — second run prints `already installed — nothing to do.`
